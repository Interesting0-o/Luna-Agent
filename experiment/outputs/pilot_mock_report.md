### 2.3 Mock 模式局限性

由于 mock 模式使用随机噪声替代 LLM 状态推断：

1. **条件 B 的状态演化 = 随机游走**（~N(0, 0.05) 每轮），不反映真实 LLM 的推断能力
2. **Hurst 指数不可用**（4 个轨迹点不足以计算 R/S 统计量）
3. **LLM-as-Judge 无法运行**（需要 DeepSeek API Key）
4. **感知层不稳定**（Ollama qwen2.5:7b 生成 JSON 格式不稳定，约 60% 失败率）

> 这些局限在真实运行中（使用 DeepSeek 作为感知和生成模型）将自然解决。

## 3. 深度分析设计

### 3.1 可以回答的问题（真实运行后）

1. **数学引擎是否产生了可检测的因果结构？**
   - 如果 A 的 Hurst 指数 > B 的 Hurst 指数 → 有结构（A 的状态演化非随机）
   - 如果 A 的表内分歧度 > B 的表内分歧度 → 口是心非被数学引擎捕获
   - 预期：A 有 >0.5 的 Hurst，B 接近 0.5（随机游走）

2. **LLM 能否在无数学引擎的情况下维持一致性？**
   - B 的跨轮连续性 vs A 的跨轮连续性
   - B 的状态分布 vs A 的状态分布（极端值频率）
   - 关键：B 的状态推断是否倾向于"中庸化"（集中在 0 附近）

3. **状态注入是否比无状态更好？**
   - A/B 的情感一致性评分 vs C
   - 如果 A ≈ B > C → 状态注入有价值，来源不重要
   - 如果 A > B > C → 数学引擎是必要条件

4. **数学引擎在哪些场景最有价值？**
   - 按场景类别分析（关系升温 vs 冲突对抗 vs ...）
   - 预期：高强度情感场景（冲突/重负）中 A 的改善最大
   - 日常闲聊中可能 A ≈ C（低刺激下差异不显著）

### 3.2 失败模式分析（待真实数据）

```
场景类型         数学引擎优势    推测原因
─────────────   ───────────   ───────────────────────
关系升温          中～高        需要细腻的状态过渡
冲突对抗          高            需要快速但连续的状态转变
日常闲聊          低            低刺激下状态变化小
情感重负          高            复杂情绪需要多层解耦
矛盾信号          最高          "口是心非"的核心场景
```

## 6. 框架架构决策记录

### 为什么 mock 模式有用

1. **调试管道逻辑** — 在不消耗 API 配额的情况下验证 3 种条件的分支逻辑
2. **验证指标计算** — 确保 auto_metrics 能正确处理各种边界情况
3. **测试序列化** — 确保 numpy → JSON → numpy 的往返转换无损
4. **预演全流程** — 从场景加载到报告生成的完整管道验证

### 为什么条件 B 用独立 LLM 调用

实验方案要求条件 B 的"状态推断调用与回复生成调用分离"，防止：
- 状态推断"作弊"（回复生成时隐式利用了状态信息）
- 状态缓存泄漏（同一对话中的状态推断影响后续生成）

使用 `temperature=0.3` 的独立 model.invoke() 调用，回复生成使用默认设置。

### 为什么 LLM-as-Judge 使用 DeepSeek

虽然最优选择是使用与生成模型**不同提供商**的模型（如用 Claude 评判 DeepSeek），
但由于项目中无 Claude API Key，退而使用 DeepSeek 自身。

缓解措施：
- temperature=0.0（确定性输出）
- 3 次重复评分取均值
- 回复顺序随机化（消除位置偏差）
- 在报告中标注"同源偏差"的局限性
