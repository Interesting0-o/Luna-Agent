# A/B 实验方案：验证数学引擎的边际价值

> **目标**：量化数学状态引擎相对于纯 LLM 方案在情感一致性、角色保持和"口是心非"表达上的增量价值。
>
> **日期**：2026-07-12
> **状态**：方案待评审

---

## 1. 为什么需要这个实验

CRITIQUE.md 中最致命的指控是第三条：

> *"LLM 的涌现情感表征已被证明比任何手工工程更丰富、更可信，'数学可解释'就变成了以牺牲质量为代价换取'我知道数字在变'。"*

目前没有任何证据反驳这一点。数学引擎的 250+ 参数、4 步管线、11 条约束可能正在产生**无法被用户感知的质量差异**——也可能确实产生了可感知的差异。没有实验就没有答案。

**核心问题**：数学引擎的存在，是否让 LLM 生成的角色回复在情感连贯性、角色一致性和表达丰富度上显著优于无引擎方案？

---

## 2. 三组实验条件

### 条件 A（处理组 — 完整数学引擎）

当前生产管线：

```
用户输入
  → perception_node（DeepSeek 提取刺激向量）
    → state_engine_node（完整 4 步管线：防御→反馈→动力学→表面）
      → state_formatter_node（数值向量 → 中文"导演笔记"）
        → llm_node（带 state_description 生成回复）
```

### 条件 B（对照组 — LLM 自报状态）

```
用户输入
  → perception_node（DeepSeek 提取刺激向量——与 A 相同）
    → [LLM 状态推断] 用独立 LLM 调用，根据对话历史 + 刺激向量推断当前状态
      → state_formatter_node（数值向量 → 中文"导演笔记"——与 A 相同）
        → llm_node（带 state_description 生成回复——与 A 相同）
```

**关键**：条件 B 的 LLM 状态推断调用**与最终回复生成调用分离**，确保状态推断不会"作弊"。

LLM 状态推断的 prompt 设计：

```
## 任务
根据以下对话历史和感知到的刺激信号，推断 [角色名] 此刻的心理状态。

## 对话历史
{conversation_history}

## 感知到的刺激信号（从用户输入中提取）
{stimuli_vector_with_labels}

## 角色人格特征
{traits_description}

## 需要输出的状态（JSON 格式）
{
  "internal_state": {
    "energy": -1.0~1.0, "stress": -1.0~1.0, "loneliness": -1.0~1.0,
    "insecurity": -1.0~1.0, "irritation": -1.0~1.0, "longing": -1.0~1.0,
    "social_battery": -1.0~1.0, "mental_fatigue": -1.0~1.0
  },
  "relationship_state": {
    "affection": -1.0~1.0, "trust_bond": -1.0~1.0, "intimacy": -1.0~1.0
  },
  "surface_state": {
    "expressiveness": -1.0~1.0, "warmth": -1.0~1.0, "sharpness": -1.0~1.0,
    "softness": -1.0~1.0, "enthusiasm": -1.0~1.0, "restraint": -1.0~1.0,
    "vulnerability": -1.0~1.0
  }
}
```

### 条件 C（基线组 — 无状态注入）

```
用户输入
  → perception_node 跳过（无刺激提取）
    → state_engine_node 跳过
      → state_formatter_node 跳过
        → llm_node（仅角色 prompt + 对话历史，无任何状态描述）
```

条件 C 建立最底层基线：如果条件 A/B 都无法显著优于 C，数学引擎根本不应存在。

## 3. 评估体系

### 3.1 自动指标（低开销，可批量运行）

| 指标 | 计算方法 | 测量什么 |
|------|----------|----------|
| **跨轮状态连续性** | 相邻轮次状态向量的余弦相似度，取方差 | 情感过渡是否平滑 |
| **表面-内部分歧度** | `\|surface - internal\|` 的 L2 范数 | "口是心非"的程度——数学引擎应在此项显著高于 B |
| **状态极端值频率** | 状态值落在 [-1.0, -0.8] ∪ [0.8, 1.0] 的比例 | LLM 自报状态是否倾向于"中庸化"（回避极端值） |
| **状态随机游走检验** | 状态轨迹的 Hurst 指数 | 状态演化是否具有结构，而非白噪声 |

### 3.2 LLM-as-Judge（中开销，核心评估）

使用 **不参与本实验的第三方 LLM**（Claude 或 GPT-4o），对生成的回复进行盲评：

**评分维度**（每个 1-5 Likert）：

| 维度 | 判定 prompt 核心问题 |
|------|---------------------|
| **情感一致性** | "角色的情绪表达与对话历史中累积的事件是否一致？是否存在情绪突变或对重大事件缺乏反应？" |
| **角色保真度** | "角色的语言风格、态度、行为模式是否符合其设定人格（高傲、依恋焦虑、口是心非）？" |
| **内心-外表张力** | "角色是否展现了内心真实感受与其表面表达之间的不一致/张力？" |
| **自然度** | "从对话角度看，这段回复是否自然、不做作？" |

**校准**：每轮评分使用 3 个随机打乱的回复（A/B/C 各一），评分者不知道条件标识。每轮重复 3 次取均值以降低评分噪声。

### 3.3 人工评估（小规模，高成本）

**方案**：招募 5 名熟悉角色扮演的评估者，每人评估 10 组对话（每组 5 轮交互）。

**流程**：
1. 评估者阅读整个对话历史（5 轮）
2. 每轮展示 3 个回复（A/B/C，顺序随机，无标识）
3. 评估者按上述 4 个维度评分（1-5）
4. 额外回答："整体而言，哪个版本的回复让你感觉角色最有生命力？"

**统计模型**：混合效应模型（固定效应 = 条件，随机效应 = 评估者 + 对话情景）

## 4. 实验设计细节

### 4.1 测试对话集

需要 20 个有标注的对话场景，覆盖不同情绪情境：

| 类别 | 数量 | 示例 |
|------|:----:|------|
| 关系升温 | 4 | 表白、关心、亲密靠近 |
| 冲突对抗 | 4 | 争吵、指责、冷落 |
| 日常闲聊 | 4 | 问候、分享、调侃 |
| 情感重负 | 4 | 道歉、袒露脆弱、告别 |
| 矛盾信号 | 4 | 反话、欲言又止、模棱两可 |

每个场景固定为 5 轮交互（3 轮建立上下文 + 2 轮关键测试）。

**种子对话生成**：先用条件 C（无状态）走 3 轮建立基础对话，然后分支为 A/B/C 三组条件继续 2 轮。这确保前三轮上下文在所有条件下相同。

### 4.2 随机化与盲法

- **回复顺序随机化**：每次评分时 A/B/C 的显示顺序随机排列
- **标签脱敏**：评分界面仅显示"回复 1/2/3"，不透露条件
- **条件内随机种子**：所有条件下使用相同的随机种子（Langevin 噪声等）

### 4.3 统计功效

基于 pilot 假设：
- 效应量：Cohen's d = 0.5（中等效应）
- 统计功效：80%（β = 0.2）
- 显著性水平：α = 0.05（双边）
- 组间相关性（ICC）：0.3
- LLM-as-Judge 评分次数：每回复 3 次

**所需样本量**：20 场景 × 5 轮 × 3 条件 = 300 回复 × 3 次评分 = 900 评分点

**可检测的最小效应**：在 900 评分点下，可检测 d > 0.25 的效应。

## 6. 预期结果与决策树

### 可能的结果

| 结果 | 数据模式 | 含义 | 行动 |
|------|----------|------|------|
| **A > B > C** | 数学引擎显著优于 LLM 自报和无状态 | 数学引擎有正价值 | 维持，继续优化 |
| **A ≈ B > C** | 有状态优于无状态，但来源不重要 | 状态注入有价值，数学引擎是开销 | 简化：用 LLM 自报替代数学引擎 |
| **A ≈ B ≈ C** | 无差异 | 状态注入无意义 | 废弃数学引擎，聚焦 prompt 工程 |
| **B > A > C** | LLM 自报优于数学引擎 | 数学引擎正在"拖后腿" | 立即废弃，转 LLM 方案 |
| **A < C** | 无状态反而更好 | 状态注入正在损害质量 | 全面重新设计 |

### 决策准则

```
if A 在情感一致性上显著高于 B（p < 0.05, d > 0.3）：
  → 维持数学引擎路线，优先解决感知精度问题
elif A ≈ B 但两者均显著高于 C：
  → 数学引擎降级为可选模块，默认使用 LLM 自报
elif A ≈ B ≈ C 或 B > A：
  → 废弃数学引擎，重新定位项目
```

## 7. 技术细节

### 7.1 条件 B 的 LLM 状态推断

**要点**：
- 使用与生产 LLM **不同**的模型实例（避免状态被缓存或泄漏到回复生成）
- 温度 = 0.3（低随机性，确保状态推断稳定）
- 输出约束：强制 JSON 格式 + bounds 检查（[-1, 1]）
- 状态推断轮次之间**不持久化**——每轮从对话历史 + 刺激向量独立推断
- 但为了公平对比，条件 B 也接收上一轮的状态描述作为额外上下文

### 7.2 时间衰减的处理

- 条件 A：使用现有 `apply_time_decay()`（数学衰减）
- 条件 B：LLM 状态推断时，在 prompt 中注入时间间隔信息（"距离上次对话已过去 X 小时"），让 LLM 自行考虑衰减
- 条件 C：不处理（无状态）

### 7.3 成本计算

| 项目 | 条件 A | 条件 B | 条件 C |
|------|:------:|:------:|:------:|
| 感知（DeepSeek） | 1 次 | 1 次 | 0 次 |
| 数学引擎 | 4 步管线 | 0 | 0 |
| LLM 状态推断 | 0 | 1 次（小型模型） | 0 |
| 回复生成 | 1 次 | 1 次 | 1 次 |

条件 B 增加一次小型 LLM 调用，总成本增加约 15-25%。全量实验预计成本：
- DeepSeek tokens：~15M input / ~3M output
- 预估费用：$2-5 USD

## 8. 局限性与已知偏差

1. **LLM-as-Judge 的自身偏差**：评分 LLM 可能偏好与自己风格相近的回复。缓解：使用与生成 LLM 不同的模型评分 + 多次评分取均值。
2. **条件 B 的 prompt 设计偏差**：状态推断 prompt 的质量直接影响条件 B 的效果。如果 prompt 设计不佳，条件 B 会被人为压低。缓解：状态推断 prompt 需经过 3 轮迭代调试。
3. **短期对话限制**：5 轮对话不足以暴露数学引擎在长程（50+ 轮）场景中的优势。缓解：本次实验仅验证短程差异，长程差异作为后续实验。
4. **单一角色限制**：仅测试"月下誓约"一个角色。结论的泛化性有限。缓解：作为第一阶段实验，后续可扩展角色。

```python
# run_experiment.py (伪代码)
def run_condition(condition: str, scenarios: list[dict]) -> dict:
    """运行指定条件的所有场景，返回收集的回复和状态日志。"""
    results = {"responses": [], "state_trajectories": []}
    for scenario in scenarios:
        state = initialize_state(scenario["traits"])
        conversation = scenario["seed_conversation"]  # 前 3 轮共享
        for turn in scenario["test_turns"]:  # 后 2 轮
            # 1. 感知（仅 A/B）
            if condition in ("A", "B"):
                stimuli = perception(turn["user_input"], state)
            # 2. 状态更新
            if condition == "A":
                state = math_engine(state, stimuli, ...)
            elif condition == "B":
                state = llm_state_inference(conversation, stimuli, ...)
            # 3. 格式化 + 生成
            state_desc = format_state(state)
            response = llm_generate(conversation, state_desc)
            # 4. 记录
            results["responses"].append(response)
            results["state_trajectories"].append(copy(state))
            conversation.append((turn["user_input"], response))
    return results
```
